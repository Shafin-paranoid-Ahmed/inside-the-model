Force data through a narrow bottleneck and the network must learn what matters.

<Step title="Copy the input, through one number">

A network trained to output its own input sounds pointless: the answer is already in the question. It stops being pointless when the input has to squeeze through a narrow gap on the way. Then the network cannot copy, so it has to work out what is worth keeping. A network built this way is called an **autoencoder**.

Here the data are 600 points in the plane, scattered along two interlocking half-moons. Each point is two numbers. The network squeezes every point into **one** number and then must rebuild the point from that number alone. Two networks of 32 hidden units each did this, trained in your browser when the page loaded.

Watch the points slide off the plane onto the line, then come back out. Before training the rebuilt points are scattered around the centre, 1.765 away from their originals on average (as a squared distance). After training the average is **0.053**, and the rebuilt points sit on a thin curve that runs along both moons. One number is enough to say where on that curve a point belongs.

</Step>

<Step title="Encoder, bottleneck, decoder">

An autoencoder is two networks back to back. The **encoder** $f$ squeezes each input $\mathbf x$ into a short **code** $z$. The **decoder** $g$ rebuilds an input from the code: $\hat{\mathbf x} = g(z)$, read "x-hat", the rebuilt point. The narrow middle, where the code lives, is the **bottleneck**, and the set of all possible codes is the **latent space** ("latent" means hidden: nobody labelled these numbers, the network invented them). Here $\mathbf x$ has 2 numbers and $z$ has 1.

The figure follows one training point from near the left tip of the upper moon, and dims the rest. The point $\mathbf x = (-1.90, -0.32)$ goes into the encoder and comes out as the single number $z = -2.32$. The decoder turns that number into $\hat{\mathbf x} = (-1.90, -0.12)$. It is close but not exact: the squared error is **0.041**, and the orange dashed line marks the miss.

<LatentSpace client:visible model="ae" mode="focus" />

<details>
<summary>Show the math</summary>

$$
z = f(\mathbf x), \qquad \hat{\mathbf x} = g(z), \qquad f: \mathbb R^2 \to \mathbb R, \quad g: \mathbb R \to \mathbb R^2 .
$$

Both are small tanh networks: $f$ has layer sizes $2 \to 32 \to 32 \to 1$ and $g$ has $1 \to 32 \to 32 \to 2$. The last layer of each is linear, so the code and the output can be any real numbers.

</details>

<details>
<summary>Show the code</summary>

```python
import torch.nn as nn

encoder = nn.Sequential(
    nn.Linear(2, 32), nn.Tanh(),
    nn.Linear(32, 32), nn.Tanh(),
    nn.Linear(32, 1),          # the bottleneck: one number per point
)
decoder = nn.Sequential(
    nn.Linear(1, 32), nn.Tanh(),
    nn.Linear(32, 32), nn.Tanh(),
    nn.Linear(32, 2),
)
z = encoder(x)                 # x has shape (batch, 2), z has shape (batch, 1)
x_hat = decoder(z)             # shape (batch, 2)
```

</details>

</Step>

<Step title="Reconstruction loss">

Nobody tells the network what the code should be. It only gets one score: how far the rebuilt point is from the original. The **reconstruction loss** is the squared distance between them, averaged over the training points. Backpropagation (see [backprop in an MLP](/learn/neural-networks/backprop-mlp/)) pushes that number down by adjusting the decoder and the encoder together, so the encoder learns to write codes the decoder can read.

The timeline replays the training. Each frame shows the decoder as it was at that step: the teal curve is everything it draws as the code slides along the line. At step 0 it draws a short stroke through the middle of the plane, touching neither moon, and the average error is **1.765**. By step 750 the curve already follows both moons and the error is **0.083**. At the end, step 1500, it is **0.053**. The chart is logarithmic, so equal heights are equal ratios: most of the improvement happens early.

<LatentSpace client:visible model="ae" mode="train" />

<details>
<summary>Show the math</summary>

For training points $\mathbf x_1, \dots, \mathbf x_N$:

$$
L = \frac{1}{N} \sum_{i=1}^{N} \left\lVert \mathbf x_i - g\big(f(\mathbf x_i)\big) \right\rVert^2 .
$$

Training takes 1,500 steps of Adam on random batches of 64 points.

</details>

</Step>

<Step title="Why the bottleneck must be narrow">

Give the code as many numbers as the input has, and the network no longer has to learn anything. It can pass the point straight through and get a nearly perfect score. Low error alone does not mean the network understood the data.

This figure runs a second autoencoder whose code has **two** numbers, and adds three probe points that are not on either moon. The error drops to **0.00034**, about 150 times smaller than the 0.053 with a one-number code, and the probe points come back where they started: the one at (1.4, 0.8) is rebuilt at (1.44, 0.67), far from both moons. Look at the plane on the right: the codes are just the points again, in a different frame. This network has learned the identity and nothing about the moons.

<LatentSpace client:visible model="ae" mode="tour" latentDim={2} probes />

The one-number network cannot do that. It can only draw points on its curve, so it has to find the curve the data lies near. Lower error was not the goal. What the code captures is.

</Step>

<Step title="Exploring the latent space">

Every number on the code line decodes to some point, so sliding along the line draws the curve the decoder has learned. The marker sweeps from the smallest code to the largest and back. The orange and blue bars count how many training points have each code, split by moon.

Both moons share one code line. The upper moon's codes run from −2.58 to 0.22 and the lower moon's from −0.13 to 2.54, so they meet near zero and there is no empty stretch between them. Instead the decoder's curve has to cross from one moon to the other, and for a short stretch of codes, about −0.04 to 0.06, the decoded point is in the empty middle between the moons. Watch the marker pass zero: the decoded point leaves the upper moon, crosses the middle (the point turns into a cross) and arrives at the lower moon. That bridge is about 2% of the code line.

<Step title="Sampling new points from an autoencoder">

If the decoder turns any code into a point, picking codes at random looks like a way to invent new data. This is the idea behind **generative models**, and it half works here.

The figure draws 300 codes at random and decodes each one. First they come from the range of codes the training points used, −2.6 to 2.5. Of the 300, **295** (98%) decode onto the data, and the few that miss, drawn as crosses, are the ones that land on the bridge from the last step. Then the same is done with codes from −4 to 4, a range nobody told the network about: only **253** (84%) land on the data, because outside the range it saw, the decoder simply carries on its curve into empty space.

An autoencoder gives no rule for which codes to use. Here we read the right range off the training data, and the easy two-moons shape forgives us. For real data the codes can sit in odd shapes, and a random code is often garbage. The [variational autoencoder](/learn/graphs-generative/vaes/) fixes this by training the codes to follow a known distribution that you can sample from.

</Step>

<Step title="Denoising autoencoders">

A cleverer training task: corrupt the input with random noise and ask for the clean point back. Now the network cannot copy, whatever the size of its code. A **denoising autoencoder** learns where the data lives and pushes any point towards it.

The figure adds noise of a growing size to 150 training points. Each grey dot is a noisy input, each teal dot is what the network returns for it, and the pink arrow joins them. The network was trained at noise level 0.25. Wait for that level: the average distance from a point to the nearest data centre is **0.20** before cleaning and **0.13** after, and the arrows from points that strayed furthest are the longest. Each one ends on the curve of a moon. At noise 0 the average gets worse (0.07 before, 0.13 after): the decoder can only output points on its one thin learned curve, so even clean points that sat off-centre in a moon are pulled onto it.

That direction, from a noisy point toward the data, is exactly what [diffusion models](/learn/graphs-generative/diffusion/) learn at many noise levels, and they use it to make new data.

<LatentSpace client:visible model="dae" mode="denoise" />

<details>
<summary>Show the code</summary>

The only change from an ordinary autoencoder is what goes in and what the target is:

```python
x_noisy = x + 0.25 * torch.randn_like(x)
loss = ((decoder(encoder(x_noisy)) - x) ** 2).sum(dim=1).mean()   # target is the clean x
```

</details>

</Step>

<Step title="Common misconceptions">

**You might think an autoencoder is a generative model.** Actually it only compresses and rebuilds. It gives no rule for choosing codes, so sampling works only when you already know a good range, and a wider guess lost 14% of the points here (step 6). The VAE adds that rule.

**You might think lower reconstruction error means a better autoencoder.** Actually a code as wide as the input drives the error to almost zero (0.00034 against 0.053) by copying, and learns nothing about the shape of the data (step 4).

**You might think the code numbers mean something to a human.** Actually they are whatever helps reconstruction. The code −2.32 is not a "left" or an "upper": any smooth reshaping of the line, such as stretching it or flipping it, would work as well after the decoder is retrained.

**You might think an autoencoder with linear layers is something new.** Actually with linear layers and squared error it finds the same subspace as principal component analysis ([PCA](/learn/classic-ml/pca/)). The tanh layers are what let the code line bend along the moons.

**You might think a denoising autoencoder only removes noise.** Actually it learns which way the data lies from any point. That direction is the quantity diffusion models are trained to estimate.

</Step>

<Step title="Check yourself">

<details>
<summary>1. Why does a one-number code suffice for the two moons?</summary>

Because the points lie close to one curve, and a position along a curve is a single number. The decoder draws the curve, the code says where on it.

</details>

<details>
<summary>2. What happens to a point between the moons when it goes through the one-number autoencoder?</summary>

It comes back on the curve, not where it was. The decoder can only produce points on its curve, so the encoder picks the code whose point is nearest.

</details>

<details>
<summary>3. Why can a two-number code on two-number data reach almost zero error without being useful?</summary>

Nothing is squeezed out, so the pair of networks can learn the identity. It rebuilds every point, including ones that are not on the moons, so it has not learned anything about them.

</details>

<details>
<summary>4. A linear autoencoder with a one-number code on 2D data learns what?</summary>

The first principal direction: the line through the data that keeps the most variance, which is what PCA finds.

</details>

<details>
<summary>5. In the denoising figure, where does the arrow from a point far from the data point?</summary>

Toward the nearest part of the data, one of the moons. The further the point has strayed, the longer the arrow.

</details>

</Step>
